Dongseong Silicone Order Management POC – Lean PRD

1. Product Summary

동성실리콘 POC는 기존 엑셀 기반 주문접수대장을 웹 기반 주문 관리 시스템으로 전환하기 위한 초기 단계다.

이 시스템은 사람이 직접 주문을 입력하고, 주문 상태를 관리하며, 생산 대상 주문을 생산중 탭에서 확인할 수 있도록 하는 최소 기능을 구현한다.

POC의 목적은 엑셀 중심 운영에서 데이터베이스 기반 주문 관리 구조로 전환 가능성을 검증하는 것이다.

세부 UI 구조 및 인터랙션은 Order Management UI Specification을 단일 UI 기준(Source of Truth)으로 따른다.

⸻

2. Problem

현재 동성실리콘의 주문 관리 프로세스는 엑셀 기반 주문접수대장을 중심으로 운영되고 있으며 다음과 같은 문제가 발생한다.
	•	엑셀 파일이 무거워 오류와 충돌이 자주 발생한다
	•	동시 접근이 어렵다
	•	주문 상태 관리가 명확하지 않다
	•	주문 전달 과정이 체계적으로 기록되지 않는다
	•	생산팀이 실시간 생산 대상 주문을 확인하기 어렵다

이로 인해 주문 누락, 생산 전달 실수, 커뮤니케이션 혼선이 발생한다.

POC는 주문 데이터를 데이터베이스 기반으로 관리하여 Single Source of Truth(SSOT) 구조를 만드는 것을 목표로 한다.

⸻

3. Goal

이 POC의 목표는 다음을 검증하는 것이다.
	1.	엑셀 없이 주문접수대장을 웹 시스템으로 운영할 수 있는가
	2.	주문 생성, 수정, 취소, 생산 전달을 하나의 UI에서 처리할 수 있는가
	3.	상태 기반 탭 구조로 주문 흐름을 명확히 관리할 수 있는가
	4.	생산 대상 주문을 별도 화면 없이 생산중 탭으로 관리할 수 있는가

⸻

4. Users

4.1 주문 입력 담당자

사무실에서 주문을 등록, 수정, 취소하고 생산팀 전달을 수행하는 사용자

4.2 생산팀 사용자

생산중 상태의 주문을 조회하는 사용자

POC에서는 생산팀 전용 화면을 별도로 구현하지 않으며, 생산중 탭이 생산 대상 목록 역할을 수행한다.

⸻

5. In Scope

POC에서 구현되는 기능은 다음과 같다.

5.1 주문 관리
	•	주문 생성
	•	주문 수정
	•	주문 취소
	•	주문 상태 변경
	•	다중 선택 작업

5.2 상태 기반 주문 관리

주문은 다음 상태를 가진다.
	•	active: 접수/작업 가능
	•	released: 생산팀 전달
	•	completed: 주문 lifecycle 완료
	•	cancelled: 주문 취소

화면 탭 라벨은 접수, 생산중, 출하 완료, 삭제됨을 유지하되 각각 active, released, completed, cancelled에 매핑한다.

5.3 생산팀 전달

주문을 생산팀으로 전달하면
	•	주문 상태가 active → released 로 변경된다
	•	생산중 탭에서 조회된다

개별 주문 및 다중 선택 주문 전달을 지원한다.

5.4 주문 리스트 UI

메인 화면은 항상 주문 리스트다.

리스트 기능
	•	주문 조회
	•	접수 탭에서 주문 수정
	•	접수 탭에서 주문 취소
	•	접수 탭에서 생산팀 전달
	•	접수 탭에서 다중 선택 작업

5.5 주문 입력 UI

주문 생성 및 수정은 우측 Drawer UI에서 수행한다.

입력 영역
	•	주문 접수 정보
	•	고객사 및 담당자
	•	제품
	•	납기

⸻

6. Out of Scope

다음 기능은 POC 범위에 포함되지 않는다.
	•	이메일 주문 자동 수집
	•	PDF 주문 파싱
	•	AI 기반 주문 인식
	•	고객사/담당자 신규 등록 기능
	•	제품/설계도 신규 등록 기능
	•	고객사/담당자/제품/설계도 기준정보 삭제 기능
	•	설계도 파일 관리
	•	생산 일정 자동 계산
	•	completed 상태 변경 기능
	•	복구 기능
	•	검색, 정렬, 페이지네이션 등 부가 리스트 기능
	•	재고 관리
	•	외부 시스템 연동

고객사/담당자 및 제품은 기존 데이터 목록에서 선택하는 방식으로만 사용한다.

UI에는 신규 등록 버튼이 표시되지만 실제 기능은 구현하지 않으며, 클릭 시 추후 개발 예정 안내를 Toast로 제공한다.

⸻

7. Core Workflow

7.1 주문 생성 흐름
	1.	사용자가 새 주문 버튼을 클릭한다
	2.	주문 입력 Drawer가 열린다
	3.	주문 정보를 입력한다
	4.	저장 시 주문이 접수 상태로 생성된다
	5.	Drawer가 닫힌다
	6.	Toast가 표시되고 주문 리스트에 반영된다

7.2 주문 수정 흐름
	1.	접수 탭 리스트에서 수정 버튼 클릭
	2.	Drawer 수정 모드 오픈
	3.	기존 데이터 로드
	4.	수정 후 저장
	5.	Drawer가 닫힌다
	6.	Toast가 표시되고 리스트에 반영된다

7.3 생산팀 전달 흐름
	1.	접수 탭에서 개별 또는 다중 주문 선택
	2.	생산팀 전달 실행
	3.	확인 모달 승인
	4.	주문 상태가 released로 변경
	5.	접수 탭에서 제거
	6.	생산중 탭에서 조회 가능
	7.	Toast가 표시된다

7.4 취소 흐름
	1.	접수 탭에서 개별 또는 다중 취소 실행
	2.	확인 모달 승인
	3.	주문 상태가 cancelled로 변경
	4.	삭제됨 탭에서만 조회 가능
	5.	Toast가 표시된다

주문 취소는 물리 삭제가 아닌 상태 변경 방식이다.

7.5 Drawer 이탈 흐름
	1.	사용자가 닫기 버튼, 바깥 영역 클릭, 또는 ESC로 Drawer 닫기를 시도한다
	2.	미저장 변경이 없으면 즉시 닫힌다
	3.	미저장 변경이 있으면 확인 모달이 표시된다
	4.	사용자는 계속 편집 또는 닫기를 선택한다

⸻

8. Status Model

주문 상태는 다음과 같다.
	•	active
	•	released
	•	completed
	•	cancelled

상태 전이
	•	신규 주문 생성 → active
	•	생산팀 전달 → released
	•	취소 → cancelled
	•	모든 출하예정 건 완료 → completed

POC에서는 completed 상태 변경 기능을 구현하지 않으며, 출하 완료 탭은 주문 lifecycle 완료 상태인 completed 주문을 조회하는 탭으로 사용한다.

탭별 액션 정책
	•	접수(active): 수정, 생산팀 전달, 취소, 다중 선택 가능
	•	생산중: 조회만 가능
	•	출하 완료: 조회만 가능
	•	삭제됨: 조회만 가능

⸻

9. Authentication

POC에서는 단순 로그인 기능만 구현한다.

목적
	•	주문 접수자 기록
	•	최소한의 사용자 식별

구성
	•	Supabase Auth 기반 이메일/비밀번호 로그인
	•	주문 생성 시 접수자는 로그인 사용자명 또는 이메일로 자동 기록
	•	사용자 역할은 기술스택 정의서의 A, P, E를 기준으로 한다
	•	A — Administrative (사무직)
	•	P — Production (현장직, 팀장 포함)
	•	E — Executive (임원)

포함되지 않는 기능
	•	기술스택 정의서에 정의된 A/P/E 외의 복잡한 권한(Role) 관리
	•	세분화된 관리자 권한 시스템
	•	세분화된 접근 제어

⸻

10. Functional Requirements

10.1 주문 리스트

리스트는 다음 정보를 표시한다.
	•	주문번호
	•	주문요청일
	•	고객사
	•	담당자
	•	채널
	•	납기
	•	상태

접수 탭에서는 추가로 다음 요소를 표시한다.
	•	선택 체크박스
	•	관리 액션

10.2 개별 액션

접수 탭의 각 주문 행에서 다음 기능을 제공한다.
	•	수정
	•	생산팀 전달
	•	취소

생산중, 출하 완료, 삭제됨 탭에서는 개별 액션을 제공하지 않는다.

10.3 다중 선택 작업

사용자는 접수 탭에서 여러 주문을 선택하여 다음 작업을 수행할 수 있다.
	•	선택 취소
	•	선택 주문 생산팀 전달

다중 선택은 현재 화면에 보이는 행 기준으로만 동작한다.

다중 수정은 허용하지 않는다.

10.4 주문 입력 Drawer

생성/수정 Drawer는 동일 UI를 재사용한다.

구성
	•	주문 접수
	•	고객사 및 담당자
	•	제품
	•	납기

UI 규칙
	•	우측 슬라이딩 Drawer
	•	배경 리스트 비활성화
	•	내부 세로 스크롤
	•	하단 저장 버튼 고정
	•	미저장 변경 시 닫기 전 확인 모달 표시

10.5 주문 접수 입력

입력 필드
	•	주문 요청일
	•	채널
	•	기타 채널명
	•	주문 담당자 (로그인 계정)

10.6 고객사 및 담당자
	•	고객사 + 담당자 세트 선택
	•	검색 기능 제공
	•	선택 전 저장 불가
	•	신규 등록 버튼 노출
	•	클릭 시 추후 개발 예정 Toast 표시

10.7 제품/설계 선택
	•	주문 1건당 제품/설계 1개 선택
	•	주문 수량 필수
	•	기존 제품 목록에서 선택
	•	신규 등록 버튼 노출
	•	클릭 시 추후 개발 예정 Toast 표시

10.8 납기 입력

납기 유형
	•	일반 출하
	•	분할 출하

검증
	•	일반 출하: 납기일 필수
	•	분할 출하: 출하일/수량 입력
	•	분할 수량 합계 = 주문 수량

10.9 리스트 표시 규칙
	•	리스트 컬럼 너비는 고정한다
	•	데스크톱 기준 고정 폭 레이아웃을 사용한다
	•	좁은 화면에서는 테이블 가로 스크롤을 허용한다
	•	셀 텍스트는 한 줄로 표시한다
	•	넘치는 텍스트는 ellipsis(...) 처리한다
	•	잘린 값은 hover 시 전체 값을 확인할 수 있어야 한다

11. Order Number Generation

주문번호는 시스템에서 자동 생성한다.

형식

YYMMDD-####

예

260315-0001

260315-0002

규칙
	•	날짜 기준은 주문 생성일
	•	같은 날짜 내 순번 증가
	•	순번은 4자리 zero-padding
	•	주문 수정 시 번호 변경 없음
	•	취소된 주문번호는 재사용하지 않음
	•	DB에서 생성하며 unique constraint로 중복 방지

13. UI / Styling Stack

POC 프론트엔드 구현은 다음 스택을 기본 원칙으로 사용한다.
	•	UI Components: IBM Carbon Design System 사용
	•	Chart / Visualization: Carbon Charts 사용
	•	Styling: Carbon Design System 스타일과 컴포넌트 패턴을 우선 사용

구현 가이드라인
	•	모든 UI 컴포넌트는 기본적으로 Carbon 컴포넌트를 기반으로 구현한다
	•	테이블, 모달, 토스트, 폼, 탭, Drawer/Side Panel은 Carbon 패턴을 우선 적용한다
	•	본 POC에서 차트가 필요한 경우 Carbon Charts를 사용한다
	•	불필요한 custom CSS 및 custom animation은 지양한다

이 원칙은 디자인 일관성, 구현 속도, 유지보수성, 인터랙션 품질을 확보하기 위한 기본 기준으로 적용한다.

⸻

14. Data Assumptions
	•	고객사 및 담당자 데이터는 기존 데이터셋을 사용한다
	•	제품 데이터는 기존 제품 목록을 사용한다
	•	POC에서는 일부 샘플 데이터만 사용해도 충분하다
	•	주문 데이터는 DB를 기준 데이터로 사용한다

⸻

15. Success Metrics

POC 성공 기준
	1.	주문을 웹 UI에서 생성할 수 있다
	2.	기존 주문을 수정할 수 있다
	3.	주문을 생산팀으로 전달할 수 있다
	4.	전달된 주문이 생산중 탭에서 조회된다
	5.	취소된 주문이 삭제됨 탭으로 이동한다
	6.	엑셀 없이 주문 상태를 관리할 수 있다
