**프로젝트**: 동성실리콘 Digital Transformation
**작성일**: 2026-03-28
**문서 유형**: Information Architecture (IA) 초안

---

## 1. IA 설계 원칙

1. **주문 중심 구조**: 모든 화면은 "주문"을 핵심 객체로 연결된다. POC는 주문 현황을 중심으로 구성하고, 생산 현황과 출하 현황은 후속 확장 화면으로 주문 단위 추적이 가능하도록 설계한다.
2. **흐름 추적 중심**: POC에서는 주문 접수 → 생산 전달까지를 구현하고, 후속 확장에서 공정 진행 → 출하 실적 흐름을 연결한다.
3. **권한별 접근 단순화**: A — Administrative (사무직) / P — Production (현장직, 팀장 포함) / E — Executive (임원) 세 역할의 접근 범위를 메뉴 수준에서 구분하여, 역할별로 필요한 화면만 노출한다.
4. **목록 + 상세 패턴 일관성**: 주요 객체(주문, 설계, 고객)는 목록 화면과 상세/입력 화면의 2단 구조를 일관되게 사용한다.
5. **경량성 유지**: 별도 대시보드, 통계, 알림 등 기능리스트 외 요소를 추가하지 않는다. 진입 즉시 실무 화면으로 연결되는 단순한 구조를 유지한다.

## 2. 전체 메뉴 구조

좌측 사이드바 기준 1depth / 2depth 구조.

```
- 주문
  - 주문 입력
  - 주문 현황
    - 주문 상세 (주문 현황 목록에서 진입, 별도 메뉴 아님)
- 생산 (후속)
  - 생산 현황
- 출하 (후속)
  - 출하 현황
- 기준정보
  - 설계 관리
  - 고객 관리
```

> **구조 정리 메모**
> - "주문 상세"는 독립 메뉴가 아니라 주문 현황 목록에서 행 클릭 시 진입하는 구조적 화면이다.
> - 메뉴 depth는 최대 2단으로 제한하며, 3단 이하로 들어가는 경우는 없다.
> - 권한에 따라 메뉴 항목 일부가 숨겨지거나 비활성화된다 (권한별 접근 구조 참조).

## 3. 화면 구조 상세

### 주문 입력

- **목적**: 이메일/카카오톡/전화로 수신된 발주를 웹 화면에 직접 입력한다.
- **주요 사용자**: A — Administrative (사무직)
- **주요 기능**: 고객 조회, 설계번호 조회, 주문 수량 입력, 출하예정일 입력
- **표시 정보**: 고객명(조회 선택), 설계번호, 업체명·품명·규격·부서코드(설계번호 조회 시 자동 채워짐), 발주 수량, 발주 채널, 출하예정일(복수 날짜 분할 입력 가능)
- **가능한 액션**: 고객 검색 및 선택 / 설계번호 입력 후 사양 자동 조회 / 출하예정일 1건 이상 행 추가 / 주문 저장
- **연결 화면**: 저장 완료 후 → 주문 현황
- **비고**: 설계번호 조회는 입력 후 자동 연동 방식. 출하예정일은 동일 주문에 대해 날짜별 수량 분할 입력 지원.

---

### 주문 현황

- **목적**: 등록된 전체 주문의 운영 상태(active/released/completed/cancelled)를 목록으로 확인하고 관리한다.
- **주요 사용자**: A — Administrative (사무직), P — Production (현장직, 팀장 포함), E — Executive (임원)
- **주요 기능**: 주문 현황 조회, 주문 수정, 생산팀 전달, 주문 취소
- **표시 정보**: 주문번호, 고객명, 설계번호, 품명, 규격, 부서코드, 수량, 출하예정일, 주문 운영 상태, 전달 여부
- **가능한 액션**:
  - (A) 행 선택 후 수정 / 취소 / 생산팀 전달 (단일 또는 다중 선택)
  - (A/P/E) 행 클릭 → 주문 상세 진입
  - 필터: 부서코드, 진행 상태, 날짜 범위 등 기본 필터
- **연결 화면**: 주문 상세 (행 클릭) / 주문 입력 (신규 입력 버튼)
- **비고**: P와 E는 조회 및 상세 진입만 가능. 수정·취소·전달 액션은 A 전용.

---

### 주문 상세

> **구조 정리 목적으로 도출된 화면** — 기능 추가 아님. 주문 현황 목록에서 단일 주문을 선택할 때 표시되는 상세 뷰.

- **목적**: 단일 주문의 전체 정보(주문 내용, 출하예정일, 생산 진행 상태, 출하 실적)를 한 화면에서 확인한다.
- **주요 사용자**: A, P, E
- **주요 기능**: 주문 내용 확인, 출하예정일 확인, 후속 생산 진행 단계 확인, 후속 출하 실적 확인
- **표시 정보**: 주문 기본 정보 전체 / 출하예정일 목록(날짜·수량) / 후속 공정 진행 단계 및 담당자 / 후속 출하 실적(출고일·실제출고수량)
- **가능한 액션**:
  - (A) 주문 수정 이동 / 생산팀 전달
  - (P) 후속 공정 진행 상태 변경 이동
  - 뒤로 가기 → 주문 현황
- **연결 화면**: 주문 현황 (뒤로) / 주문 수정 (A) / 생산 현황 (후속)
- **비고**: 주문-생산-출하 전체 흐름을 단일 주문 기준으로 조회하는 허브 화면.

---

### 생산 현황 (후속 확장, POC 본 구현 제외)

- **목적**: 후속 생산 화면에서 부서별 주문의 생산 진행 단계와 담당자를 조회하고, 현장직이 공정 상태를 갱신한다.
- **주요 사용자**: P — Production (현장직, 팀장 포함), E — Executive (임원, 조회만)
- **주요 기능**: 생산 진행 현황 조회, 공정 진행 상태 변경
- **행 단위**: **주문 기준 생산 작업(production task)**. 하나의 주문은 여러 생산 작업으로 나뉠 수 있다.
- **표시 정보**: 주문번호, 고객명, 품명, 규격, 부서코드, 생산 작업 수량, 현재 진행 단계, 담당자
- **정렬**: 1순위 — 주문 등록일 오름차순 (먼저 접수된 주문 먼저)
- **가능한 액션**:
  - (P) 행 선택 → 공정 진행 단계 변경 (시작 대기 → 계획중 → 생산중 → 일시중지 → 생산완료) / 담당자 기록
  - (P/E) 부서코드 기준 필터 조회
- **연결 화면**: 주문 상세 (주문 단위 확인) / 출하 현황
- **비고**: POC에서는 생산 작업 레코드를 실제 생성하지 않고, 주문이 생산팀에 전달되면 `orders.status = released`까지만 관리한다. 생산 현황은 후속 확장 화면이다.

---

### 출하 현황 (후속 확장, POC 본 구현 제외)

- **목적**: 후속 출하 화면에서 출하 실적을 입력하고, 출하건별 진행 상태 및 미출고 현황을 조회한다.
- **주요 사용자**: A (조회), P (입력·조회), E (조회)
- **주요 기능**: 출하 실적 입력, 출하 현황 조회 (미출고 포함)
- **행 단위**: **출하예정 건(delivery schedule) 하나당 한 행**. `delivery_schedules`가 출하 예정과 현재 출하 상태를 함께 가진다.
- **출하 상태 흐름**:
  - `출하 준비 (0/전체)` → `일부 출하 (n/전체)` → `출하 완료 (전체/전체)`
  - 중단 시: `일부 출하 (n/전체)` → `출하 중지 (n/전체)`
  - 괄호 안 숫자는 출고 완료 수량 / 해당 출하건 예정 수량
- **표시 정보**: 출하예정일, 주문번호, 고객명, 품명, 규격, 부서코드, 출하예정수량, 출하 상태 (완료/전체), 출고일, 납기요구일, 비고
- **가능한 액션**:
  - (P) 출하 실적 입력 (출고일, 실제출고수량 → 상태 자동 갱신)
  - (A/P/E) 기간 필터, 출하 상태 필터 조회 (미출고 = 출하 준비 + 일부 출하 + 출하 중지)
- **연결 화면**: 주문 상세 (주문 단위 추적)
- **비고**: 미출고 현황은 별도 화면 없이 이 화면 내 상태 필터로 처리. 실제 출하 이력은 `shipment_records`에 기록되고, 누적 출고 수량과 출하 상태는 `delivery_schedules`에서 관리한다.

---

### 설계 관리

- **목적**: 제품/설계 기준정보를 조회한다. 설계번호는 주문 입력 시 제품 사양 조회의 키값으로 사용된다.
- **주요 사용자**: A — Administrative (사무직), E — Executive (임원)
- **주요 기능**: 설계 조회
- **표시 정보**: 설계번호, 업체명, 품명, 규격, 부서코드 (목록 형태)
- **가능한 액션**:
  - (A/E) 설계번호·품명 검색 조회
- **연결 화면**: 주문 입력 (설계번호 조회 시 참조)
- **비고**: POC에서는 설계 신규 등록, 수정, 삭제 기능을 제공하지 않는다. 후속 확장을 위해 DB에는 soft delete 구조를 유지한다.

---

### 고객 관리

- **목적**: 고객 정보를 조회한다. 주문 입력 시 고객 검색의 기준 데이터다.
- **주요 사용자**: A — Administrative (사무직), E — Executive (임원)
- **주요 기능**: 고객 조회
- **표시 정보**: 고객명, 기타 식별 정보 (목록 형태)
- **가능한 액션**:
  - (A/E) 고객명 검색 조회
- **연결 화면**: 주문 입력 (고객 조회 시 참조)
- **비고**: POC에서는 고객/담당자 신규 등록, 수정, 삭제 기능을 제공하지 않는다. 후속 확장을 위해 DB에는 soft delete 구조를 유지한다.

## 4. 핵심 객체 기준 구조

### 주문

- **설명**: 이 시스템의 핵심 객체. 모든 화면이 주문 단위로 연결된다.
- **주요 속성**: 주문번호, 고객 (→ 고객 참조), 설계번호 (→ 설계 참조), 품명, 규격, 부서코드, 발주수량, 발주채널, 전달 여부, 등록일시
- **연결되는 화면**: 주문 입력, 주문 현황, 주문 상세, 생산 현황, 출하 현황
- **관련 액션**: 입력, 수정, 취소, 생산팀 전달

---

### 출하예정일

- **설명**: 1개 주문에 대해 날짜별로 분할 입력되는 출하 예정 정보. 주문에 종속된 객체.
- **주요 속성**: 주문번호 (→ 주문 참조), 예정일, 예정수량
- **연결되는 화면**: 주문 입력, 주문 상세
- **관련 액션**: 입력 (주문 입력 시 함께 처리)

---

### 생산 진행 상태

- **설명**: 주문 단위로 관리되는 생산 작업 상태. 하나의 주문은 여러 생산 작업으로 나뉠 수 있다.
- **주요 속성**: 주문번호 (→ 주문 참조), 생산 작업 수량, 진행 단계 (시작 대기 / 계획중 / 생산중 / 일시중지 / 생산완료), 담당자, 변경일시
- **연결되는 화면**: 생산 현황, 주문 상세
- **관련 액션**: 공정 진행 상태 변경 (P)

---

### 출하 실적

- **설명**: 출하예정일 단위로 관리되는 실제 출고 기록. 출하 상태와 누적 출고 수량은 `delivery_schedules`에서 관리하고, 실제 출고 이력은 `shipment_records`에 기록한다.
- **주요 속성**: 출하예정일 ID (→ 출하예정일 참조), 출고일, 실제 출고 수량, 입력자
- **상태 전이**: `출하 준비` → `일부 출하` → `출하 완료` (중단 시 `출하 중지`)
- **연결되는 화면**: 출하 현황, 주문 상세
- **관련 액션**: 출하 실적 입력 (P) — 출고일·실제출고수량 입력 시 상태 자동 갱신

---

### 설계

- **설명**: 제품 사양의 기준 데이터. 설계번호가 키값으로 주문 입력 시 자동 조회에 사용된다.
- **주요 속성**: 설계번호, 업체명, 품명, 규격, 부서코드
- **연결되는 화면**: 설계 관리, 주문 입력 (조회 참조)
- **관련 액션**: 조회

---

### 고객

- **설명**: 발주처 정보. 주문 입력 시 선택의 기준 데이터.
- **주요 속성**: 고객명, 기타 식별 정보
- **연결되는 화면**: 고객 관리, 주문 입력 (조회 참조)
- **관련 액션**: 조회

---

## 5. 화면 간 이동 흐름

### 사무직(A): 주문 접수 및 생산 전달 흐름

```
주문 입력
  └→ 고객 조회 (고객 관리 데이터 참조, 팝업/인라인)
  └→ 설계번호 입력 → 사양 자동 조회 (설계 관리 데이터 참조)
  └→ 출하예정일 입력 (날짜별 분할)
  └→ 저장
    └→ 주문 현황 (목록 확인)
      └→ 주문 상세 (행 클릭)
        └→ 생산팀 전달 (단일 또는 다중 선택 후 전달)
```

---

### 현장직(P): 후속 생산 진행 상태 갱신 및 출하 입력 흐름

```
후속 생산 현황 (전달된 주문의 생산 작업 목록 확인)
  └→ 행 선택 → 공정 진행 단계 변경
       (시작 대기 → 계획중 → 생산중 → 일시중지 → 생산완료)
       담당자 기록 및 저장
  └→ 주문 상세 (주문 내용 확인 필요 시)
    └→ 후속 생산 현황 복귀

후속 출하 현황 (출하예정일 기준 출하건 목록)
  └→ 행 선택 → 출하 실적 입력 (출고일, 실제출고수량)
       상태 자동 갱신: 출하 준비 → 일부 출하 → 출하 완료
       (중단 시 → 출하 중지)
  └→ 미출고 필터로 잔여 건 확인
```

---

### 임원(E): 진행 현황 조회 흐름

```
주문 현황 (전체 주문 진행 상태 조회)
  └→ 주문 상세 (단일 주문 상세 확인)

생산 현황 (후속, 부서별 생산 진행 단계 조회)

출하 현황 (후속, 출하 실적 및 미출고 현황 조회)
```

## 6. 권한별 접근 구조

| 권한 | 접근 가능 메뉴 | 주요 목적 | 비고 |
|------|--------------|-----------|------|
| A — Administrative (사무직) | 주문 입력, 주문 현황, 설계 관리, 고객 관리, 출하 현황 (후속 조회) | 주문 데이터 입력·수정·취소, 생산팀 전달, 기준정보 조회 | 생산 현황 공정 단계 변경 불가 |
| P — Production (현장직, 팀장 포함) | 주문 현황 (조회), 생산 현황/출하 현황 (후속) | POC에서는 생산중 주문 조회. 후속에서 공정 진행 상태 변경, 출하 실적 입력 | 주문·기준정보 입력·수정·삭제 불가 |
| E — Executive (임원) | 주문 현황, 설계 관리, 고객 관리, 생산 현황/출하 현황 (후속 조회) | 전체 운영 현황 조회 | 조회 전용. 입력·수정·삭제·전달 액션 비활성화 |

## 7. IA 관점에서의 설계 판단

### 주문 상세 화면이 필요한가?

**판단**: 필요하다.
**이유**: 주문 현황 목록은 다수 주문을 스캔하는 용도이며, 출하예정일·생산 진행 상태·출하 실적은 목록 컬럼으로 모두 표시하기 어렵다. 단일 주문의 전체 흐름(주문→생산→출하)을 한 화면에서 확인하는 허브가 필요하다. 단, 별도 메뉴로 노출하지 않고 목록 행 클릭으로 진입하는 구조로 충분하다.

---

### 생산 현황과 출하 현황은 주문 중심으로 연결되는가?

**판단**: 연결된다.
**이유**: 후속 확장에서 생산 작업은 주문에 직접 연결되고, 출하 실적은 출하예정일을 통해 주문에 연결된다. 각 화면은 주문 단위로 추적 가능하며, 주문 상세에서 생산 작업과 출하예정/출하 이력을 통합 조회할 수 있다. 화면 간 직접 이동(생산 현황 ↔ 출하 현황)보다 주문 상세를 경유하는 흐름이 구조적으로 더 명확하다.

---

### 설계/고객 입력은 POC에서 필요한가?

**판단**: POC에서는 불필요하다.
**이유**: POC에서는 설계/고객 기준정보의 신규 등록, 수정, 삭제 기능을 제공하지 않는다. 기준정보 화면은 조회 중심으로 유지하고, 입력·삭제는 후속 기준정보 관리 화면에서 검토한다.

---

### 홈/대시보드가 필요한가?

**판단**: 현재 POC 범위에서는 불필요하다.
**이유**: 기능리스트에 대시보드 기능이 없고, 통계·알림·집계 기능도 정의되어 있지 않다. 권한별로 로그인 후 기본 진입 화면을 다르게 설정하는 것으로 대체할 수 있다 (A → 주문 현황, P → 주문 현황의 생산중 탭, E → 주문 현황). 대시보드 추가는 POC 이후 단계에서 검토한다.

---

### 권한별 첫 진입 화면은 어떻게 다를 가능성이 있는가?

**판단**: 역할에 따라 기본 진입 화면을 분리하는 것이 적절하다.
**이유**: A는 주문 처리가 주 업무이므로 주문 현황이 자연스러운 첫 화면이다. P는 POC에서 별도 생산 화면 없이 생산중 탭을 통해 생산 대상 주문을 조회한다. E는 전체 현황 파악이 목적이므로 주문 현황을 기본으로 설정할 수 있다. 별도 홈 화면 없이 로그인 시 역할별 첫 화면으로 직접 라우팅하는 방식이 단순하고 현실적이다.

---

## 8. 최종 IA 요약

DSS의 IA는 **주문 → 생산 → 출하**라는 단방향 운영 흐름을 화면 구조로 그대로 구현한다. 메뉴는 주문 / 생산 / 출하 / 기준정보의 4개 영역으로 구성되며, 총 화면 수는 7개 내외로 경량하게 유지된다. 모든 화면은 주문번호를 중심으로 연결되며, 주문 상세가 주문·생산·출하 정보를 통합 확인하는 허브 역할을 한다. 권한 구조는 A — Administrative (사무직) / P — Production (현장직, 팀장 포함) / E — Executive (임원)의 세 역할로 단순화되어 화면 수준에서 접근 범위가 분리된다. 설계·고객 기준정보는 주문 입력의 보조 데이터로 기능하며, 별도 입력 화면 없이 목록 내 처리로 충분하다. 이 구조는 엑셀 기반 분산 운영에서 발생하는 누락·오입력·현황 불투명 문제를, 최소한의 화면 수로 데이터 기반 구조로 전환하기 위해 설계되었다.
